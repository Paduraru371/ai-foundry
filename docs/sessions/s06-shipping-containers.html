Session 6 · AI Engineering on Azure

Shipping the container — from your laptop to a public URL

Today the application stops being something you run and becomes something that runs.

For five sessions the backend has lived on your machine. There is a Dockerfile, there is a docker compose up, and yet the instruction has consistently been run the Python on the host. That was not an oversight and it was not a limitation of containers — it was a precise consequence of one fact: a container on your laptop has no identity. This session explains that fact properly, shows exactly what a development image does that a shipped image must not, and then walks the whole road to Azure: a registry, an image, an environment, a managed identity, configuration, secrets, logs, revisions and a URL anyone can open. Every command is given for Windows PowerShell first, with the bash equivalent beside it, because that is what is on your screen.

The question behind today

Why the Python has been running on your machine

You have a Dockerfile. You have a docker compose up that starts three services. And yet, every time the agent features came up, the instruction was: stop the API container and run uvicorn on the host. That looks like an admission that the containers do not work. It is not. It is the consequence of a single, precise fact, and once you see it the whole picture reorganizes itself.

The fact

az login does not log you in. It writes a token cache into a folder inside your Windows user profile — %USERPROFILE%\.azure. Anything that can read that folder inherits your Azure identity. A container cannot read it: it has its own filesystem, its own users, and no access to your profile unless you deliberately mount it in.

So a container is not "denied" Azure — it is simply anonymous. And an anonymous process has exactly one way left to prove who it is: a key. That is why docker-compose.yml sets AZURE_AI_AUTH=key for the API service. It is a workaround, and it works — but only for the half of Azure that accepts keys.

The container is not the problem. The laptop is the one place where a container has no identity of its own.

Which turns the question inside out. It is not "why can't I run this in Docker?" It is "why would I run it in Docker on the one machine where containers are least useful?" A container's job is to make an application reproducible somewhere else. On your own machine you already have the source, the interpreter and the login; the container adds isolation you do not need and removes an identity you do. In Azure the trade reverses completely, and the identity story gets better than it is locally: the platform hands the container a credential nobody had to create, store or rotate.

The sentence to remember

You have not been avoiding containers. You have been running the container where the container is worth having — Qdrant and the console — and running the one piece that needs your personal identity as your personal user. Today the API stops needing your identity, because it gets one of its own.

Fundamentals

What is actually inside an image

Before shipping one it is worth being exact about what an image is, because almost every deployment failure is a violation of one of these three properties.

PropertyWhat it meansWhat it forbids
Self-contained Everything the program needs to start is inside: interpreter, libraries, code Depending on a file on the host, a folder you mounted, or a tool you happen to have installed
Immutable The layers are read-only and content-addressed; the same digest is byte-identical anywhere Writing anything you want to keep into the container filesystem
Configured from outside Behaviour comes from environment variables at start time, not from what was baked in Building one image per environment; baking secrets into layers

An image is a stack of layers, each the filesystem difference produced by one instruction. Ordering them from least to most volatile is not a style preference — it is what makes rebuilds fast, because every layer above a changed one is discarded.

FROM ghcr.io/astral-sh/uv:python3.12-bookworm-slim
Debian + Python + uv — changes when you upgrade Python, so almost never
COPY pyproject.toml uv.lock
changes when you add a dependency
RUN uv sync --frozen --no-dev
the expensive layer — reused as long as the lock file is identical
COPY app ./app
changes every time you edit a line — deliberately last
CMD uvicorn app.main:app --host 0.0.0.0 --port 7799
metadata, not a layer: what to run when the container starts

Swap the last two COPYs and every code edit reinstalls every dependency. This is the single most common cause of a two-minute build that should take two seconds.

Two details in that file earn their place. --frozen tells uv to install exactly what uv.lock pins and to fail rather than silently resolve something newer — the build is reproducible or it does not happen. --no-dev leaves the test and tooling dependencies out of the shipped image: smaller, and a smaller attack surface.

And --host 0.0.0.0, which looks like a detail and is not. The default, 127.0.0.1, means accept connections that originate inside this machine — and a container is its own machine. A server bound to loopback inside a container is unreachable from everywhere, including from the host that started it. It is the most common "the container is running but nothing answers" of all.

The distinction that matters today

A development image and a shipped image are not the same image

Until this session, both Dockerfiles in this repository were written for one job: give you hot reload inside a container. Read them with shipping in mind and the problems are immediate.

what the API Dockerfile used to end with 
CMD ["uv", "run", "--no-sync", "uvicorn", "app.main:app",
     "--host", "0.0.0.0", "--port", "7799", "--reload"]
docker-compose.yml — the other half of the same trick 
volumes:
  - ./app:/srv/app          # your editor writes straight into the container

--reload makes uvicorn watch the filesystem and restart when a file changes. That is only useful because the bind mount replaces the image's copy of /srv/app with the folder on your disk. The two are a pair. Push that image to a registry and run it in Azure, where there is no bind mount, and you get a server that spends CPU watching files that will never change, restarts on a stray write, and — worse — an image whose behaviour silently depended on source it does not contain.

The fix is the standard one: the image carries the shippable default, and compose adds the development behaviour back for development only.

code/backend/Dockerfile — now 
# A shippable default: the code is IN the image, and the server does not watch the
# filesystem for edits. Development puts --reload back through `command:` in
# docker-compose.yml, where the source is also bind-mounted — the two belong
# together, and neither belongs in an image you push to a registry.
CMD ["uv", "run", "--no-sync", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "7799"]
code/backend/docker-compose.yml — now 
api:
  build: .
  command: ["uv", "run", "--no-sync", "uvicorn", "app.main:app",
            "--host", "0.0.0.0", "--port", "7799", "--reload"]
  volumes:
    - ./app:/srv/app

Nothing about your daily workflow changes. docker compose up still hot-reloads. But docker run on the same image now behaves like production, which is the entire point: the thing you test is the thing you ship.

The console had a bigger problem

The console image ran npm run dev — the Vite development server. That is not a small compromise. A dev server compiles modules on demand, serves them unminified, keeps a websocket open for hot reload, and needs the entire node_modules tree at runtime. It is also the component that has been proxying every API call, which is why the browser never met a CORS error.

Shipping it means doing both jobs properly: compile React once, and give the proxying job to something built for it. The Dockerfile now has two targets from one file — dev for compose, prod by default — and nginx.conf.template forwards the same route list that vite.config.js forwards in development.

Why the API URL must be settable at start time

A compiled React bundle is static files: anything you inline at build time is frozen into them, so a build-time API URL would mean one image per environment. Keeping the proxy in nginx and the URL in an environment variable means one image serves development, staging and production — configured, not rebuilt. The nginx:alpine image substitutes environment variables into any file under /etc/nginx/templates/ when it starts, which is why the file is called nginx.conf.template.

The core mechanic

The identity problem, exactly

The application never asks for a token directly. It constructs a DefaultAzureCredential, and that object tries a fixed sequence of ways to obtain one, stopping at the first that succeeds. Understanding that sequence explains every authentication outcome you have seen this week.

#CredentialWhere it looksWins when…
1EnvironmentCredentialAZURE_CLIENT_ID, AZURE_CLIENT_SECRET, AZURE_TENANT_IDyou gave the process a service principal
2WorkloadIdentityCredentiala projected token filerunning in Kubernetes with workload identity
3ManagedIdentityCredentiala local metadata endpoint the platform providesrunning in Azure — Container Apps, App Service, a VM
4VisualStudioCodeCredentialthe VS Code Azure extensionyou signed in inside the editor
5AzureCliCredential%USERPROFILE%\.azure, via the az executableyou ran az login — this is your laptop's lane
6AzurePowerShellCredentialthe Az.Accounts moduleyou used Connect-AzAccount instead

Now the whole week reads cleanly. On your machine lane 5 wins. In a plain container none of the lanes can win, so the code falls back to a key. In Azure Container Apps lane 3 wins — before it ever reaches the CLI lane, and without any secret existing.

A real failure worth memorizing

A backend started from a shell whose PATH did not include the Azure CLI failed with AzureCliCredential: Azure CLI not found on path — even though az login had been done hours earlier and every other terminal worked. Lane 5 does not read the token cache itself; it shells out to az. If the process cannot find the executable, the lane fails, and the error is about a missing program rather than a missing login. When a credential error surprises you, read which lane failed and why: the chain always tells you.

The three ways to give a process an identity

LaneWhat it isSecret to protectUse it for
Managed identity Azure creates a principal, attaches it to your compute, and rotates its credential for you none — there is nothing to leak Anything running in Azure. Always the first choice.
Service principal An application identity with a client secret or certificate you hold a secret with an expiry date CI/CD pipelines, and containers running outside Azure
API key A shared string that identifies the resource, not the caller a secret with no expiry and no audit trail Local experiments, and services that offer nothing better

The ordering is not moral, it is operational. A key cannot be scoped to one operation, cannot be attributed to a person or a service in an audit log, and does not expire — so a leaked key is valid until somebody notices and rotates it. A managed identity has no string to leak in the first place, and every call it makes is attributable to a named principal.

The fix

Managed identity — and the code that does not change

When you deploy a container app with --system-assigned, Azure creates a service principal in your Entra tenant, ties its lifetime to that app, and exposes a metadata endpoint inside the container. The SDK calls that endpoint, gets a token, and uses it. Delete the app and the principal is deleted with it.

Inside the running container

↓ returns a short-lived token

Roles are granted to the identity, not written into the app. Revoking access is a role removal, not a redeploy.

Not one line of Python changes

The same DefaultAzureCredential that reads your az login on your laptop reads the platform identity in Azure. The only difference between the two environments is which lane of the chain answers first — and that is decided by the environment, not by your code. This is what the abstraction was for.

One consequence worth stating plainly, because it inverts the usual intuition: the deployed application is more secure than your development setup, and simpler. Locally you juggle a key in .env, or a service principal with a secret that expires. Deployed, there is no key, no secret, no expiry, and a role assignment you can read and revoke from one place.

Check your .dockerignore before the first push

An image is built from everything in the folder you point at, and .env lives in that folder. If it is not excluded, your keys are baked into a layer — and a layer is permanent, so deleting the file in a later instruction does not remove it. Both .dockerignore files in this repository already exclude .env, .venv and node_modules. Verify it yourself rather than trusting this sentence:

PowerShell — prove the secret is not in the image 
docker build -t libra-api:check code\backend
docker run --rm libra-api:check ls -la /srv          # no .env should appear

# and search every layer, not just the final filesystem
docker history --no-trunc libra-api:check | Select-String -Pattern "AZURE_|API_KEY"
The decision nobody warns you about

Where the state goes

A container filesystem is temporary. When a replica is replaced — a new revision, a scale event, a node moving — everything written inside it is gone. That is not a defect; it is the property that makes replicas interchangeable. But it means every piece of state your application keeps has to live somewhere that outlives a replica.

This application keeps exactly one: the vector store. Locally that is a Qdrant container with a named volume, and a named volume is a folder on your machine. It does not travel.

OptionWhat you getWhat you take onVerdict for this course
Azure AI Search Managed index; keyword, vector and hybrid retrieval; semantic ranking; role-based access A monthly bill, and a different query API Use this. The app already speaks it — /tools/azure-search/*
Qdrant as a second container app The same database you develop against, no code change at all A persistent volume, backups, upgrades, and its security — all yours Valid, and instructive. More moving parts than today allows
Qdrant with no volume It starts Your index disappears on every restart, silently Never. This is the trap

This is the payoff for the work in the previous session. Azure AI Search was not added for variety — it is the piece that makes the application deployable, because it is the only part of the retrieval stack that a container does not have to own. The service holds the index; the container holds nothing and can be replaced at any moment.

The general rule

Before you deploy anything, list what it writes. Every item on that list needs a home outside the container: a managed database, a search index, blob storage, a queue. If something on the list has no home, you have not finished designing the deployment — you have only postponed discovering it.

Choosing

Where a container can run in Azure

There are five reasonable answers and they differ mainly in how much of the platform you are asked to operate. Pick by the amount of infrastructure you want to own, not by the feature list.

ServiceModelScales to zeroYou operateReach for it when
Container Apps Serverless containers on managed Kubernetes you never see yes The image and the configuration An HTTP API or a background worker — this course
App Service Classic PaaS that also accepts a container no (always-on plan) The image, the plan, the slots You already run App Service and want one more thing beside it
Container Instances One container, no orchestration at all manual Everything above the container A one-off job or a demo lasting an afternoon
Kubernetes (AKS) The full cluster, yours with work Nodes, networking, upgrades, ingress, the lot You have a platform team and reasons
Functions Event-driven; can run a container yes The function code Short, triggered work rather than a long-lived server

We use Container Apps, and the reasons are specific to what we built. It scales to zero, so an idle course project costs nothing. It issues an HTTPS certificate for you. It supports managed identity directly, which is the whole point of today. And it keeps revisions, so shipping a new version and rolling it back are both one command — the operational property that matters most the first time you deploy something broken.

What "serverless" means here

Not that there is no server — that you do not name one, patch one, or pay for one while nothing is happening. Underneath, Container Apps runs on Kubernetes; the deal is that the cluster is not yours to operate. With --min-replicas 0 the platform stops your last replica when traffic stops and starts one again when a request arrives. The price of that is a cold start: the first request after an idle period waits for a container to boot.

0 · Set your variables once

Every command below reads from these. Set them at the top of your session and the rest of the page is copy-paste. Names matter: a registry name must be globally unique across all of Azure, lowercase, letters and digits only.

PowerShell — edit the first four lines, run the block 
$Rg       = "libra-ai-acad"                 # your existing resource group
$Location = "swedencentral"                 # the region your Foundry resource is in
$Acr      = "acrlibra<yourname>"            # globally unique, lowercase, a-z0-9 only
$Foundry  = "libra-ai-acad-resource"        # your Foundry (AI Services) resource

$Env      = "cae-libra-acad"                # the Container Apps environment
$ApiApp   = "ca-libra-api"
$WebApp   = "ca-libra-console"

# sanity: are you where you think you are?
az account show --query "{user:user.name, subscription:name}" -o yaml

The one-command version — worth seeing once

az containerapp up --name ca-quick --resource-group $Rg --location $Location --source . --target-port 7799 --ingress external creates a registry, builds your image in the cloud, creates an environment and deploys the app — one command, about four minutes. It is a genuinely good way to see the shape of the thing before learning the parts. It also authenticates the app to the registry with an admin key and gives it no managed identity, which is precisely what the rest of this recipe exists to avoid. Use it to explore; use the steps below for anything you intend to keep.

1 · Verify what you already own

Four things must be true. Each command prints something if it is satisfied.

PowerShell 
# 1 · the resource group exists
az group show --name $Rg --query "{name:name, location:location}" -o yaml

# 2 · a chat model and an embedding model are deployed
az cognitiveservices account deployment list --name $Foundry --resource-group $Rg --query "[].{deployment:name, model:properties.model.name}" -o table

# 3 · the Foundry endpoints, which the app will need
az cognitiveservices account show --name $Foundry --resource-group $Rg --query properties.endpoints -o yaml

# 4 · your CLI is recent enough for the containerapp commands
az version --query "\"azure-cli\"" -o tsv

2 · Register the providers, add the extension

A subscription only accepts resource types whose provider is registered. Registration is a one-time, free operation per subscription and takes a minute or two the first time. Doing it now converts a confusing error later into a short wait now.

PowerShell 
az extension add --name containerapp --upgrade

az provider register --namespace Microsoft.App
az provider register --namespace Microsoft.ContainerRegistry
az provider register --namespace Microsoft.OperationalInsights   # where the logs go

# repeat until all three say Registered
az provider show --namespace Microsoft.App --query registrationState -o tsv
az provider show --namespace Microsoft.ContainerRegistry --query registrationState -o tsv
az provider show --namespace Microsoft.OperationalInsights --query registrationState -o tsv

3 · Create the container registry

A registry is where images live so that something other than your laptop can pull them. Docker Hub is a registry; Azure Container Registry is one inside your subscription, with your access control and your network rules.

PowerShell 
az acr create --name $Acr --resource-group $Rg --location $Location --sku Basic

# admin access stays OFF: the app will authenticate as itself, not with a shared password
az acr update --name $Acr --admin-enabled false

az acr show --name $Acr --query "{name:name, server:loginServer, sku:sku.name}" -o yaml

4 · Build the images — in the cloud

This is the step that surprises people, and it is the best single argument for the CLI on Windows. az acr build uploads your build context to Azure, builds the image there on Linux, and pushes it to your registry. You do not need Docker installed at all — no Desktop, no daemon, no WSL, no licence question. It also removes a whole category of "works on my machine": the build runs on the same kind of machine that will run it.

PowerShell — from the repository root 
az acr build --registry $Acr --image libra-api:v1 code\backend

# the console's Dockerfile has two targets; `prod` is the default, so nothing extra to pass
az acr build --registry $Acr --image libra-console:v1 code\frontend

az acr repository list --name $Acr -o table
az acr repository show-tags --name $Acr --repository libra-api -o table

The local alternative, for completeness

If you do have Docker and prefer to build locally, it is three steps: az acr login --name $Acr, then docker build -t "$Acr.azurecr.io/libra-api:v1" code\backend, then docker push "$Acr.azurecr.io/libra-api:v1". On an ARM Mac add --platform linux/amd64 to the build, or the image will not start in Azure — a failure that reads like a crash and is actually an architecture mismatch.

5 · Create the Container Apps environment

An environment is the shared boundary your apps live in: one virtual network, one Log Analytics workspace, one internal DNS namespace. Apps in the same environment can reach each other by name, privately. Creating it takes two to three minutes — the slowest step on this page.

PowerShell 
az containerapp env create --name $Env --resource-group $Rg --location $Location

az containerapp env show --name $Env --resource-group $Rg --query "{name:name, state:properties.provisioningState, domain:properties.defaultDomain}" -o yaml

6 · Create the API app — with a placeholder image

A deliberate order of operations. The app cannot pull from your private registry until it has an identity, and it has no identity until it exists. So it is created from a public image that always pulls, and given the real one two steps later. Doing it the other way round produces an authorization failure that reads like a missing image.

PowerShell 
az containerapp create `
  --name $ApiApp --resource-group $Rg --environment $Env `
  --image mcr.microsoft.com/k8se/quickstart:latest `
  --target-port 7799 --ingress external `
  --system-assigned `
  --min-replicas 0 --max-replicas 2 `
  --cpu 0.5 --memory 1.0Gi
FlagWhat it decides
--target-port 7799The port your process listens on inside the container. The outside is always 443
--ingress externalReachable from the internet, with a certificate Azure issues and renews. internal = only from inside the environment
--system-assignedCreate a managed identity tied to this app's lifetime. The reason this page exists
--min-replicas 0Idle costs nothing; the first request after idling pays a cold start
--max-replicas 2The ceiling. Set it deliberately — it is your defence against a runaway bill
--cpu 0.5 --memory 1.0GiPer replica. The consumption profile pairs roughly 2 GiB of memory per vCPU, so these two go together

7 · Give the identity permission to pull

PowerShell 
$principalId = az containerapp identity show --name $ApiApp --resource-group $Rg --query principalId -o tsv
$acrId       = az acr show --name $Acr --query id -o tsv

az role assignment create --assignee $principalId --role AcrPull --scope $acrId

# tell the app to authenticate to the registry as itself
az containerapp registry set --name $ApiApp --resource-group $Rg --server "$Acr.azurecr.io" --identity system

Role assignments are not instant

Entra propagates them, which usually takes seconds and occasionally a couple of minutes. If the next step fails with an authorization error, wait sixty seconds and run it again before changing anything. Re-running the same command is safe.

8 · Deploy the image you actually built

PowerShell 
az containerapp update --name $ApiApp --resource-group $Rg --image "$Acr.azurecr.io/libra-api:v1"

$apiFqdn = az containerapp show --name $ApiApp --resource-group $Rg --query properties.configuration.ingress.fqdn -o tsv
"https://$apiFqdn"

It will not answer usefully yet — it has no configuration, so it does not know which model to call. That is step 10. What this step proves is that the image was pulled from your private registry using an identity rather than a password.

9 · Grant the data-plane roles

The identity can now pull an image. It still cannot call anything. Each service needs its own role assignment, scoped to that resource and nothing wider — this is where "least privilege" stops being a slogan and becomes four commands.

PowerShell 
$foundryId = az cognitiveservices account show --name $Foundry --resource-group $Rg --query id -o tsv

# chat, embeddings, speech
az role assignment create --assignee $principalId --role "Cognitive Services User" --scope $foundryId

# the Foundry Agent Service, if you use hosted agents
az role assignment create --assignee $principalId --role "Azure AI User" --scope $foundryId

# Azure AI Search, if you moved the vector store there
$searchId = az search service show --name srch-libra-acad --resource-group $Rg --query id -o tsv
az role assignment create --assignee $principalId --role "Search Index Data Contributor" --scope $searchId

# read back exactly what this identity can do — worth doing every single time
az role assignment list --assignee $principalId --all --query "[].{role:roleDefinitionName, scope:scope}" -o table

10 · Configure it

Two kinds of value, and the difference is not cosmetic. Environment variables are visible to anyone who can read the app — endpoints, model names, feature flags. Secrets are stored encrypted, are never returned by az containerapp show, and are referenced by name.

PowerShell — secrets first 
# only if you still need one. With managed identity, most of these disappear entirely.
$searchKey = az search admin-key show --service-name srch-libra-acad --resource-group $Rg --query primaryKey -o tsv

az containerapp secret set --name $ApiApp --resource-group $Rg --secrets "search-key=$searchKey"
PowerShell — then the configuration 
az containerapp update --name $ApiApp --resource-group $Rg `
  --set-env-vars `
    "LLM_PROVIDER=azure" `
    "EMBEDDING_PROVIDER=azure" `
    "AZURE_AI_AUTH=identity" `
    "AZURE_AI_ENDPOINT=https://$Foundry.services.ai.azure.com/models" `
    "AZURE_AI_CHAT_DEPLOYMENT=gpt-5-mini" `
    "AZURE_AI_EMBEDDING_DEPLOYMENT=text-embedding-3-small" `
    "AZURE_AI_PROJECT_ENDPOINT=https://$Foundry.services.ai.azure.com/api/projects/<your-project>" `
    "AZURE_SEARCH_ENDPOINT=https://srch-libra-acad.search.windows.net" `
    "AZURE_SEARCH_INDEX=libra-docs" `
    "AZURE_SEARCH_KEY=secretref:search-key" `
    "AGENT_PERSONA=teller"

AZURE_AI_AUTH=identity — the line this whole session was for

On your laptop that setting means "use my az login". Here it means "use the identity Azure attached to this app". Same value, same code, a different lane of the credential chain. There is no key for chat, no key for embeddings, no key for the Agent Service — and the agent features that were dark in Docker are available again, because for the first time the container has a real identity.

11 · Verify from outside

PowerShell 
irm "https://$apiFqdn/health" | ConvertTo-Json -Depth 4

# the call that proves the identity works — no key involved anywhere
irm "https://$apiFqdn/agents" | ConvertTo-Json -Depth 4
#   look for:  "foundry": { "available": true, "reason": null }

$body = @{ question = "What can you help me with?"; use_rag = $false } | ConvertTo-Json
$r = irm "https://$apiFqdn/ask" -Method Post -ContentType 'application/json' -Body $body
$r.answer

Compare that with the same call at the end of Lab A, where foundry.available was false. Nothing about the application changed between the two. Only its address — and what that address implies about who it is.

12 · Deploy the console in front of it

The same pattern, one image smaller, plus the environment variable that tells nginx where to forward the API routes.

PowerShell 
az containerapp create `
  --name $WebApp --resource-group $Rg --environment $Env `
  --image "$Acr.azurecr.io/libra-console:v1" `
  --target-port 7800 --ingress external `
  --system-assigned --registry-server "$Acr.azurecr.io" --registry-identity system `
  --env-vars "API_URL=https://$apiFqdn" `
  --min-replicas 0 --max-replicas 2 `
  --cpu 0.25 --memory 0.5Gi

$webFqdn = az containerapp show --name $WebApp --resource-group $Rg --query properties.configuration.ingress.fqdn -o tsv
start "https://$webFqdn"

--registry-identity system is the shortcut for steps 6 and 7 combined: the CLI creates the identity, assigns AcrPull and configures the registry in one call. It is what you would normally write. Step 6 took the long way round on purpose, so that when this line fails — usually because your account cannot create role assignments — you know which of the three things it does went wrong.

Then close the back door

The API does not need to be on the public internet once the console fronts it. Switch it to internal ingress and it becomes reachable only from inside the environment:

PowerShell — optional, and good practice 
az containerapp ingress update --name $ApiApp --resource-group $Rg --type internal

# the internal name replaces the public one; point the console at it
$apiInternal = az containerapp show --name $ApiApp --resource-group $Rg --query properties.configuration.ingress.fqdn -o tsv
az containerapp update --name $WebApp --resource-group $Rg --set-env-vars "API_URL=https://$apiInternal"

13 · Delete everything

Knowing the teardown is part of knowing the deployment. Nothing here is precious, and an environment you cannot delete confidently is one you will hesitate to rebuild.

PowerShell 
# just the apps
az containerapp delete --name $WebApp --resource-group $Rg --yes
az containerapp delete --name $ApiApp --resource-group $Rg --yes

# the environment and the registry too
az containerapp env delete --name $Env --resource-group $Rg --yes
az acr delete --name $Acr --resource-group $Rg --yes

# or all of it, Foundry included — the nuclear option
az group delete --name $Rg --yes --no-wait
Configuration

Where each value belongs

Your .env file has about thirty entries. In a deployment they split into four groups, and putting one in the wrong group is either a leak or an inconvenience.

GroupExamplesWhere it goesWhy
Not secret, changes per environment Endpoints, deployment names, index names, AGENT_PERSONA --set-env-vars Readable by anyone who can read the app, and that is fine — being able to see them is useful
Secret, still needed A Brave or Serper search key; a third-party API key az containerapp secret set, referenced as secretref:name Encrypted at rest, never echoed back by the CLI, injected only into the container
Secret, and avoidable AZURE_AI_API_KEY, AZURE_SEARCH_KEY Nowhere — delete them and use the managed identity The best place to keep a secret is not to have one
Shared across several apps A certificate; a database password more than one service needs Azure Key Vault, read by the app's identity One place to rotate, one audit log, one set of access rules
PowerShell — Key Vault, when a secret outgrows one app 
az keyvault create --name kv-libra-acad --resource-group $Rg --location $Location --enable-rbac-authorization true
az keyvault secret set --vault-name kv-libra-acad --name search-key --value $searchKey

# let the app's identity read it — a role, not a password
$kvId = az keyvault show --name kv-libra-acad --query id -o tsv
az role assignment create --assignee $principalId --role "Key Vault Secrets User" --scope $kvId

# the app resolves the reference itself, at start, as itself
az containerapp secret set --name $ApiApp --resource-group $Rg `
  --secrets "search-key=keyvaultref:https://kv-libra-acad.vault.azure.net/secrets/search-key,identityref:system"

Follow the chain in that last command: the app authenticates to Key Vault with its managed identity, reads the secret at start, and exposes it to the process as an environment variable. The secret never appears in your shell, your repository, your CI logs or the app's own definition. That is the shape of a well-kept secret — and note it is the same identity doing the work as in every other step today.

Operating it

Logs, probes and revisions

Reading the logs

Two streams, and reaching for the wrong one wastes a lot of time. Console logs are what your process wrote to stdout and stderr. System logs are what the platform did to your container: pulled the image, started it, failed a probe, replaced it. When an app will not start at all, the answer is almost always in the system stream.

PowerShell 
az containerapp logs show --name $ApiApp --resource-group $Rg --follow --tail 50
az containerapp logs show --name $ApiApp --resource-group $Rg --type system --tail 50

# which replicas exist right now, and in what state
az containerapp replica list --name $ApiApp --resource-group $Rg -o table

Logs the platform can actually read

Container Apps collects stdout line by line. A log line that is valid JSON becomes a queryable record in Log Analytics; a multi-line Python traceback becomes several unrelated records. The argument for structured logging is worth having before you need it at three in the morning, not after.

Health probes

The platform will replace a replica that stops answering — but only if you have told it how to ask. Your application already has the endpoint: /health checks the vector store, the configured provider, and the speech and search configuration, so it fails when the app is genuinely unusable rather than merely alive.

PowerShell 
az containerapp update --name $ApiApp --resource-group $Rg `
  --liveness-probe-path /health --liveness-probe-initial-delay 15 `
  --readiness-probe-path /health
ProbeAsksWhen it fails
StartupHas it finished booting?The replica is given more time, then abandoned
ReadinessCan it take traffic right now?It is removed from the load balancer, and kept alive
LivenessIs it still working at all?The replica is killed and replaced

Revisions — shipping, and un-shipping

Every change to the image or the configuration creates a new revision: an immutable snapshot of the app's definition. Old revisions are kept, which makes a rollback a routing change rather than a rebuild.

PowerShell 
az containerapp revision set-mode --name $ApiApp --resource-group $Rg --mode multiple
az containerapp revision list --name $ApiApp --resource-group $Rg -o table

# ship v2 beside v1 and send it a tenth of the traffic
az acr build --registry $Acr --image libra-api:v2 code\backend
az containerapp update --name $ApiApp --resource-group $Rg --image "$Acr.azurecr.io/libra-api:v2"

az containerapp ingress traffic set --name $ApiApp --resource-group $Rg `
  --revision-weight <old-revision-name>=90 <new-revision-name>=10

# it is bad. put everything back — seconds, not a rebuild
az containerapp ingress traffic set --name $ApiApp --resource-group $Rg --revision-weight <old-revision-name>=100

Multi-revision mode is not the default

Out of the box an app runs in single revision mode: a new revision replaces the old one and traffic splitting is unavailable. Turn it on before you need it — which is why it is the first line of the block above. Otherwise the rollback you want at the worst possible moment is a redeploy.

This is the operational habit worth taking from today, independently of Azure. A deployment that can be undone in one command changes how a team behaves: releases get smaller and more frequent, because being wrong stops being expensive.

Tags, and why latest is a trap

latest is not a version; it is a name that means whatever was pushed last. Two replicas started ten minutes apart can be running different code, and the revision history will not show it. Tag with something that identifies the build — a git commit is the honest choice, because it makes an image traceable to a line of code.

PowerShell 
$sha = git rev-parse --short HEAD
az acr build --registry $Acr --image "libra-api:$sha" code\backend
az containerapp update --name $ApiApp --resource-group $Rg --image "$Acr.azurecr.io/libra-api:$sha"

The point of all of it

One script, from nothing to a URL

Every step in the recipe was a command, which means the whole recipe is a program. That is the argument for a cloud platform in its strongest form: not that there is a website, but that an environment is code — reviewable in a pull request, repeatable by a colleague, and rebuildable from nothing after you delete it by accident.

code/backend/scripts/azure/08-deploy-containerapp.ps1 — the shape 
param(
    [string]$ResourceGroup = "libra-ai-acad",
    [string]$Registry      = "acrlibraacad",
    [string]$Environment   = "cae-libra-acad",
    [string]$Tag           = "v1"
)
$ErrorActionPreference = "Stop"

# 1 · providers and extension     (idempotent — check before registering)
# 2 · registry                    (idempotent — az acr show first)
# 3 · build both images in ACR    (always runs; the tag is the version)
# 4 · environment                 (idempotent)
# 5 · app + identity + AcrPull    (idempotent — check the role assignment first)
# 6 · data-plane roles on Foundry and AI Search
# 7 · environment variables and secrets
# 8 · print the two URLs

Two properties make such a script worth writing, and both take deliberate effort. It must be idempotent — every step checks before it creates, so running it twice is safe and running it after a partial failure resumes rather than collapses. And it must be parameterized — names and region at the top, so the same file builds your environment and a colleague's without an edit.

The only honest test

az group delete --name $Rg --yes, then run your script. If the environment comes back — registry, images, environment, apps, identity, roles, configuration — and the URL answers, you have written infrastructure as code and you can stop being nervous around your cloud account. That confidence is the deliverable, not the script.

The next step: doing it on every commit

The same commands run in GitHub Actions with no change of substance. The only genuinely new problem is how the pipeline authenticates, and the modern answer avoids storing a secret at all: workload identity federation lets GitHub present a short-lived token that Entra trusts, for one repository and one branch.

.github/workflows/deploy.yml — the essential shape 
permissions:
  id-token: write          # lets the job request a federated token
  contents: read

steps:
  - uses: actions/checkout@v4
  - uses: azure/login@v2
    with:
      client-id:       ${{ secrets.AZURE_CLIENT_ID }}
      tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
      subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
  - run: az acr build --registry $ACR --image libra-api:${{ github.sha }} code/backend
  - run: az containerapp update --name $APP --resource-group $RG --image $ACR.azurecr.io/libra-api:${{ github.sha }}

Three identifiers, no password, and an image tagged with the commit that produced it. Notice that the last two lines are commands you already ran by hand today — which is the point. A deployment pipeline is not a new technology; it is your terminal session, written down.

The failures you will actually hit

The order to look in

System logs, then console logs, then az containerapp show for the definition, then the role assignments. Four places, in that order, resolve almost everything — and each one is a command, so you can put them in a script and stop having to remember them.

Lab B · 15 minutes

Deploy your own, and open it on a device that is not your laptop

Work in your own resource group, with your own names. Fifteen minutes is enough if the providers are already registered — do step 2 of the recipe first if you have not.

  1. Registry and images. Create your registry, then build both images with az acr build. Note how long it takes, and what it never asked you for.
  2. Environment and API app. Create the environment, then the app with --system-assigned, --min-replicas 0 and a --max-replicas you chose deliberately.
  3. Identity and roles. AcrPull on the registry, Cognitive Services User on your Foundry resource. Then read the assignments back and check the list contains nothing wider than you intended.
  4. Configuration. Set the environment variables — with AZURE_AI_AUTH=identity and no key anywhere.
  5. Prove it. Call /health and /agents over HTTPS. Record whether foundry.available is true, and be ready to say why.
  6. Console. Deploy it with API_URL pointing at your API and open it on your phone. That is the moment it stops being a local project.
  7. Then break it on purpose. Deploy a v2 whose AZURE_AI_CHAT_DEPLOYMENT names a model that does not exist. Watch it fail, find the failure in the logs, and roll back with one traffic-weight command.

Leave it running or delete it — but decide

With --min-replicas 0 the apps cost nothing while idle, so leaving them up for the rest of the week is reasonable and useful for Session 7. Azure AI Search is the exception: if you provisioned it on basic, delete it tonight and recreate it tomorrow.

Conclusions

What changed today

The question this session opened with — why are we running the Python on the host when there is a perfectly good Dockerfile? — turned out to have an answer that was not about Docker at all. A container is anonymous, and your laptop has no way to give it an identity that is not a secret. Azure does. The moment the container runs somewhere that can vouch for it, the reason to avoid containers disappears and the argument reverses completely: the deployed version is the one with no key in it.

The second thread was subtler and will outlast this platform. Almost everything that made the application pleasant to develop — hot reload, a bind mount, a dev server, a .env file, a database in a disposable container — is a development device, and each has a production counterpart that must be chosen deliberately. Nobody warns you about this, because in development none of it looks like a decision. Shipping is largely the work of finding those devices and replacing them, one at a time.

And the third: the code did not change. Not one line of Python was edited to make any of this work. What changed was configuration, identity, and where the process runs. When an abstraction is chosen well — DefaultAzureCredential is the example on this page — moving between environments becomes a matter of what is true around the code rather than what is written inside it. That is what you were buying when you accepted the extra indirection.

Takeaways

Ten things to remember

  1. A container on your laptop is anonymous. az login writes a token cache into your user profile and the container cannot see it. That is the whole reason the API ran on the host.
  2. Keys work for the data plane, not the control plane. Chat, embeddings, speech and search accept a key. The Agent Service and every ARM operation require an Entra token.
  3. Managed identity removes the secret entirely. Azure creates the principal, attaches it to the app, rotates its credential and deletes it with the app. Nothing to leak, nothing to rotate.
  4. DefaultAzureCredential is a chain, not a method. Lane 5 wins on your machine, lane 3 wins in Azure, and the error always names the lane that failed.
  5. A dev image and a shipped image are different images. --reload, bind mounts and dev servers are development devices; the image carries the shippable default and compose adds the rest back.
  6. Layer order is a performance decision. Dependencies before source, or every edit reinstalls the world.
  7. Bind to 0.0.0.0. Loopback inside a container means reachable by nothing, including the host that started it.
  8. Anything the container writes is lost. List what your app persists before you deploy it; every item needs a home outside the replica.
  9. latest is not a version. Tag with the commit, so an image can be traced back to a line of code.
  10. If it is a command, it is a program. The real test of an environment is deleting it and rebuilding it from a script.
